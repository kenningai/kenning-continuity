# v0.2.0 — Kenning Continuity

A revision now records why it was made. A chain can no longer fork, and
nothing can compact one. Two graph-analytics tools are added, and
domain-scoped projections now work.

**Breaking.** `evolve_knowledge` requires `revision_why`, and `merge_knowledge`
has been removed. With `gds_articlerank` and `gds_leiden` added, there are 24
tools.

## The reason for a revision lives on the edge

`evolve_knowledge` refuses a call without a `revision_why`, and a blank one
counts as missing. The reason is stored on the new `EVOLVED_FROM` edge,
between the two versions it explains.

A description says what an entity is. Before this release, the only place to
put the reason for a change was the description itself, so text like
"CORRECTION: …" ended up there. That text describes the record, not the
entity, and every later reader inherits the argument in place of the fact.
Put the fact in the description and the correction in `revision_why`.

The revising session is not copied onto the edge. It is already one hop away,
through the new version's `DISCOVERED` edge, which is written in the same
statement.

`get_chain_history` now returns each version's `revision_why` and the session
and director that wrote it, found by walking the graph. Versions are ordered
by their position in the chain rather than by timestamp. Revisions made before
this release come back with no reason. None is supplied for them, because a
reason nobody recorded would be a claim no session made.

## A chain is a line

Before this release, two sessions evolving the same entity at the same moment
could both succeed and leave the chain with two current versions. Finding the
current version, locking it, re-checking it under the lock and writing the
new version now all happen in one transaction. The second session waits for
the first, then is refused and told to read the new head. Both parts are
needed: without the lock the second write runs past the first, and without
the re-check under it, the second waits and then forks the chain anyway.

`evolve_knowledge` also refuses when two separate chains in one domain have a
current version with the same name. Before, it wrote a successor onto both.

If your graph may hold forks from before this release, this read-only query
finds them:

```cypher
MATCH (old:Knowledge)<-[:EVOLVED_FROM]-(n:Knowledge)
WITH old, count(n) AS successors WHERE successors > 1
RETURN old.name, successors
```

## `merge_knowledge` is removed

In this graph, the person directing a session is the author of what it
records. A version that no later version contradicts was true as of when it
was stated. A reader can see that by walking the chain, and no tool should
flatten the chain on their behalf. Compacting a chain is the system deciding
which of a person's statements stand, so the tool is gone and nothing replaces
it. To change what is held, evolve. To see less history, read less of it.

On any chain `merge_knowledge` was used on, the earlier versions were deleted,
and the `DISCOVERED` edges of the sessions that wrote them were moved onto the
surviving version. `create_knowledge` and `evolve_knowledge` give a version
exactly one discovering session. A version that carries more was given them
another way, of which a merge is one. `get_chain_history` therefore returns
`discovered_by` as a list, and shows every author rather than choosing one.

## Two more graph-analytics tools

`gds_articlerank` is PageRank with the contribution of hubs damped: a node
linked from an entity that links to everything gains less from that link. An
entity that ranks high under `gds_pagerank` and drops under `gds_articlerank`
owes its centrality to hubs, not to being widely relied on. Run both on the
same projection to see the gap.

`gds_leiden` guarantees that every community it returns is internally
connected. Louvain can return a community whose members are joined only
through nodes outside it. `gds_louvain` is kept.

Neither tool changes the ontology. They read a projection, and a projection
holds only `:Knowledge` nodes.

## Projections hold what is known now

`gds_create_projection` projects each entity once, as its current version.
Before this release, every version in an `EVOLVED_FROM` chain entered the
projection as its own node, joined to the others by the chain. An entity
revised five times counted five times in centrality, and pulled its
neighbours together in community detection. Earlier versions are history,
which `get_chain_history` reads. They are not part of the structure that
analytics measure.

An edge authored on an earlier version is not lost. It is resolved through
the chain to the current version at both ends, the same way
`get_domain_state` resolves it, and duplicates are collapsed by source,
target and type. Filtering to current versions alone would have dropped
every connection made before an entity's latest revision, so the
projection resolves edges through the chain instead. Entities with no
knowledge edges do not appear, because the projection is built from edges.

Expect centrality and community results to change on graphs with long
chains. They now describe the entities rather than their revision history.

## Domain-scoped projections

Before this release, `gds_create_projection` with a `domain` set returned
`null` and created no projection, so every analytics call against it failed.
Domain membership is now found by walking the graph, as every other tool
does: an entity belongs to a domain when a session in that domain discovered
it. With `include_cross_domain`, an edge is projected when either end belongs
to the domain. Without it, both ends must. A projection that would hold
nothing is now refused with a message naming the domain, and no `null` is
returned.

## The server reports its own version

The MCP handshake's `serverInfo.version` now reports the installed
kenning-continuity version. Before, it fell back to the version of the
underlying fastmcp library. The value is read from package metadata, so it
always matches the installed package.

## The model

`docs/design/ontology/v0.2.0.tql` makes `evolved-from` own `revision-why`, and
lets a knowledge node play `predecessor` and `successor` at most once each.
`scripts/model_probe.py` loads the model into a fresh TypeDB database for
each probe, and checks what the model should refuse as well as what it should
accept. All 12 probes give their expected verdict on v0.2.0. Run against
v0.1.1, the fork is accepted, which shows the new cardinality is what refuses
it.
